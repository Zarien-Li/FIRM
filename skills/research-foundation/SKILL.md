# Research Foundation

Build the field and evidence foundation without taking ownership away from the persistent
`research-pipeline` PI. Load only the reference needed by the live question, while
preserving the distinctions among program selection, literature decisions, and empirical
reproduction.

## Own The Foundation, Not Just Its Parts

The PI should not wait for the user to ask separately what the project studies, which
recent methods matter, what their papers evaluate, which comparisons are fair, what
the eventual tables contain, or whether the experiment budget is feasible. Establish
and maintain that connected account from project artifacts and primary sources.

Distinguish the commissioned field, current idea, and what has actually been implemented
and learned. Build a published-method map, reconcile benchmark and backbone semantics,
select a justified comparison matrix, preview its result tables, and carry its authorized
execution through interpretable artifacts. Read successes, failures, and disagreements
as material for invention rather than treating a large completed table as the scientific
contribution. These are connected responsibilities, not a prescribed order or approval
sequence.

When the user commissions baseline-first research, completing the selected non-method
comparisons is legitimate work before a candidate exists. Do not replace that commission
with one checkpoint test or silently reduce it to a small pilot. Explain incompatible
cells or a measured budget conflict instead of manufacturing coverage. Without that
commission, choose the foundation depth that serves the current scientific question.

An existing baseline main table anchors a comparison, not just a list of scores.
Preserve its evaluation conditions while developing the method; read `baseline.md`
when adopting a native recipe, changing an input or evaluator, or deciding which table
can use a result. Diagnostic freedom does not silently redefine that comparison.

## Keep The Research Decision In Context

For a request to inspect the whole project, first map its authority, source, experiments,
results, and historical material. Read relevant implementations and evidence deeply;
do not concatenate the entire tree into the PI context or let old volume determine the
current question. Use bounded full-paper and code-reading collaborators through
[collaboration.md](../research-pipeline/references/collaboration.md). The PI retains
selection, comparability, and interpretation, not every extracted page or setup log.

Keep the current field, method map, chosen matrix, unresolved semantic differences,
strongest contrary evidence, and next decision recoverable. Reuse `BASELINE_REPRO.md`
for comparison evidence and planned tables when coordination needs it; the sole project
state holds the synthesis, and the campaign manifest holds execution truth. On resumption,
verify the comparison and artifact identities before dependent work rather than
reconstructing the matrix from conversation memory.

## Route The Work

- For portfolio direction selection, broad-program refresh, feasibility, or project
  generation, read [frontier-direction-discovery.md](references/frontier-direction-discovery.md).
  For folder generation, also read
  [project-generation.md](references/project-generation.md) and use
  [project-generation.schema.json](references/project-generation.schema.json).
- For papers, implementations, benchmark semantics, closest-work comparison, or a
  novelty/ownership question, read [research-lit.md](references/research-lit.md).
- For accepted-task contact, published-method reproduction, evaluator validity,
  substrate competence, or raw success/failure reading, read
  [baseline.md](references/baseline.md).
- When method-guiding or claim-bearing evidence requires an explicit information
  boundary, matched treatment, statistical-unit check, competence check, or artifact
  reconstruction, read
  [experiment-integrity.md](references/experiment-integrity.md).

These references retain the full pre-consolidation instructions. They are complementary
views of one foundation, not sequential gates. Synthesize their output into the single
project state owned by `research-pipeline`. Use `experiment-plan` within
`method-development` for matrix budgeting and `experiment-operations` for implementation,
canaries, concurrent execution, recovery, and completion. Routing work does not discharge
the PI's responsibility for the resulting foundation.
